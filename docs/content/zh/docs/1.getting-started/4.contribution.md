## Project structure

以下是Nuxt UI项目结构中关键目录和文件的概述：

### Documentation

该文档位于`docs`文件夹中，作为Nuxt应用程序使用`@nuxt/content`从Markdown文件生成页面。有关其工作原理的详细信息，请参阅[Nuxt内容文档](https://content.nuxt.com/docs/getting-started)。以下是其结构的详细信息：

```bash
├── app/
│   ├── assets/
│   ├── components/
│   │   └── content/
│   │       └── examples   # Components used in documentation as examples
│   ├── composables/
│   └── ...
├── content/
│   ├── blog/
│   ├── docs/
│   │   ├── 1.getting-started
│   │   ├── 2.components   # Components documentation
│   │   ├── 3.composables
│   │   └── 4.typography
│   └── ...            # Landing pages (index.yml, showcase.yml...)
```

### Module

模块代码位于`src`文件夹中。下面是其结构的分解：

```bash
├── plugins/
├── runtime/
│   ├── components/        # Where all the components are located
│   │   ├── Accordion.vue
│   │   ├── Alert.vue
│   │   └── ...
│   ├── composables/
│   ├── locale/
│   ├── plugins/
│   ├── types/
│   ├── utils/
│   └── vue/
│       ├── components/
│       └── plugins/
├── theme/                 # This where the theme for each component is located
│   ├── accordion.ts       # Theme for Accordion component
│   ├── alert.ts
│   └── ...
├── utils/
└── module.ts
```

## CLI

为了使开发更容易，我们创建了一个CLI，您可以使用它来生成组件和区域设置。您可以使用`pnpm cli make`命令访问它。

### Components

可以使用以下命令创建新组件：

```bash
pnpm cli make component <name> [options]
```

可用选项：

- `--primitive`创建基本元件
- `--prose`创建散文组件
- `--content`创建内容组件
- `--template`仅生成特定模板（可用模板：`playground`、`docs`、`test`、`theme`、`component`）

范例：

```bash
# Create a basic component
pnpm cli make component my-component

# Create a prose component
pnpm cli make component heading --prose

# Create a content component
pnpm cli make component block --content

# Generate only documentation template
pnpm cli make component my-component --template=docs
```

::note
在创建新组件时，CLI将自动生成所有必要的文件，如组件本身、主题、测试和文档。
::

### Locales

您可以使用以下命令创建新的区域设置：

```bash
pnpm cli make locale --code <code>
```

区域设置名称和方向从[CLDR](https://cldr.unicode.org/)开始填充，并根据该名称验证代码。您可以使用`--name`和`--dir`标志覆盖它们。

翻译完消息后，您可以通过运行以下命令来检查您的语言环境是否与其他语言环境（消息键、占位符、名称和方向）保持一致：

```bash
pnpm test locale --run
```

::note{to="/docs/getting-started/integrations/i18n/nuxt#supported-languages"}
在文档中了解有关**i18n**的更多信息。
::

## Submit a Pull Request（PR）

在开始之前，请检查是否存在描述您正在处理的问题或功能请求的现有问题。如果存在，请对该问题发表评论，让我们知道您正在处理该问题。

如果没有，打开一个新的问题来讨论问题或功能。

### Local development

要开始本地开发，请执行以下步骤：

::steps{level="4"}

#### 将`nuxt/ui`存储库克隆到本地计算机

```bash
git clone -b v4 https://github.com/nuxt/ui.git
```

#### Enable[Corepack](https://github.com/nodejs/corepack)

```bash
corepack enable
```

#### Install dependencies

```bash
pnpm install
```

#### Generate type stubs

```bash
pnpm run dev:prepare
```

#### Start development

- 要处理位于`docs`文件夹中的**documentation**，请运行：

```bash
pnpm run docs
```

- 要使用**playground**测试Nuxt组件，请运行：

```bash
pnpm run dev
```

- 要使用**playground**测试Vue组件，请运行：

```bash
pnpm run dev:vue
```

::

::note{to="#cli"}
如果您正在实现一个新组件，请查看**CLI**部分以快速启动该过程。
::

### IDE设置

我们建议将VSCode与[ESLint扩展名](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint)一起使用。您可以在保存代码时启用自动修复和格式化。具体操作如下：

```json [.vscode/settings.json]
{
  "editor.codeActionsOnSave": {
    "source.fixAll": "never",
    "source.fixAll.eslint": "explicit"
  },
  "prettier.enable": false
}
```

::warning
由于ESLint已配置为格式化代码，因此无需使用**Prettier**复制功能。如果您在编辑器中安装了ESLint，我们建议禁用它以避免冲突。
::

### Linting

您可以使用`lint`命令来检查是否存在linting错误：

```bash
pnpm run lint # check for linting errors
pnpm run lint:fix # fix linting errors
```

### Type checking

我们使用TypeScript进行类型检查。您可以使用`typecheck`命令来检查类型错误：

```bash
pnpm run typecheck
```

### Testing

在提交PR之前，请确保运行以下测试：

```bash
pnpm run test
```

::tip
如果必须更新快照，请在测试运行完成后按`u`。
::

### Commit约定

我们使用[Conventional Committs](https://www.conventionalcommits.org/)作为提交消息，它允许基于提交自动生成更改日志。如果您还不熟悉，请阅读[guide](https://www.conventionalcommits.org/en/v1.0.0/#summary)到。

- 将`fix`和`feat`用于影响功能或逻辑的代码更改
- `docs`用于文档更改，`chore`用于维护任务

### Making a Pull Request

- 按照创建请购单时提供的[提示沿着操作](https://github.com/nuxt/ui/blob/v4/.github/PULL_REQUEST_TEMPLATE.md?plain=1

- 请确保您的PR标题符合[Conventional Committs](https://www.conventionalcommits.org/，因为一旦代码合并，将使用该标题。

- Multiple commit也没问题;不需要rebase或者强制推送。我们在合并时会使用`Squash and Merge`。

- 请确保`lint`、`typecheck`和`tests`在提交PR之前工作。避免进行不相关的更改。

我们会立即检查它。如果分配给维护人员，他们会仔细检查它。忽略红色文本;它是用于跟踪目的。
