## Projektstruktur

Hier ist eine Übersicht der wichtigsten Verzeichnisse und Dateien in der Nuxt UI-Projektstruktur:

### Dokumentation

Die Dokumentation befindet sich im Ordner `docs` als Nuxt-App, die `@nuxt/content` verwendet, um Seiten aus Markdown-Dateien zu generieren. Siehe die [Nuxt-Inhaltsdokumentation ](https://content.nuxt.com/docs/getting-started) für Details zur Funktionsweise:

```bash
├── app/
│   ├── assets/
│   ├── components/
│   │   └── content/
│   │       └── examples   # Components used in documentation as examples
│   ├── composables/
│   └── ...
├── content/
│   ├── blog/
│   ├── docs/
│   │   ├── 1.getting-started
│   │   ├── 2.components   # Components documentation
│   │   ├── 3.composables
│   │   └── 4.typography
│   └── ...            # Landing pages (index.yml, showcase.yml...)
```

Um die Entwicklung zu vereinfachen, haben wir eine CLI erstellt, mit der Sie Komponenten und Locales generieren können. Sie können mit dem Befehl `pnpm cli make` darauf zugreifen.

### Komponenten

Sie können neue Komponenten mit dem folgenden Befehl erstellen:

```bash
pnpm cli make component <name> [options]
```

verfügbare Optionen:

- `--primitive` Erstellen einer primitiven Komponente
- `--prose` Erstellen Sie eine Prosa-Komponente
- `--content` Erstellen Sie eine Inhaltskomponente
- `--template` Nur spezifische Vorlagen generieren (verfügbare Vorlagen: `playground`,`docs`,`test`,`theme`,`component`)

beispiel:

```bash
# Create a basic component
pnpm cli make component my-component

# Create a prose component
pnpm cli make component heading --prose

# Create a content component
pnpm cli make component block --content

# Generate only documentation template
pnpm cli make component my-component --template=docs
```

::note
Wenn Sie eine neue Komponente erstellen, generiert die CLI automatisch alle erforderlichen Dateien wie die Komponente selbst, das Thema, Tests und die Dokumentation.
::

### Lokales

Sie können neue Locales mit dem folgenden Befehl erstellen:

```bash
pnpm cli make locale --code <code>
```

Der Gebietsname und die Richtung werden von [CLDR](https://cldr.unicode.org/) ausgefüllt und der Code wird dagegen validiert.

Sobald Sie die Nachrichten übersetzt haben, können Sie überprüfen, ob Ihr Gebietsschema mit den anderen übereinstimmt (Nachrichtenschlüssel, Platzhalter, Name und Richtung), indem Sie Folgendes ausführen:

```bash
pnpm test locale --run
```

::note{to="/docs/getting-started/integrations/i18n/nuxt#supported-languages"}
Erfahren Sie mehr über **i18n** in der Dokumentation.
::

## Senden Sie einen Pull-Request (PR)

Bevor Sie beginnen, prüfen Sie, ob ein Problem vorliegt, das das Problem oder die Feature-Anfrage beschreibt, an der Sie gerade arbeiten. Wenn ja, hinterlassen Sie bitte einen Kommentar zu dem Problem, um uns mitzuteilen, dass Sie daran arbeiten.

Ist dies nicht der Fall, öffnen Sie eine neue Ausgabe, um das Problem oder die Funktion zu besprechen.

### Lokale Entwicklung

Um mit der lokalen Entwicklung zu beginnen, folgen Sie diesen Schritten:

::steps{level="4"}

#### Klonen Sie das `nuxt/ui`-Repository auf Ihren lokalen Computer

```bash
git clone -b v4 https://github.com/nuxt/ui.git
```

### IDE-Einrichtung

Wir empfehlen die Verwendung von VSCode zusammen mit der [ESLint-Erweiterung ](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint). Sie können die automatische Korrektur und Formatierung beim Speichern Ihres Codes aktivieren.

```json [.vscode/settings.json]
{
  "editor.codeActionsOnSave": {
    "source.fixAll": "never",
    "source.fixAll.eslint": "explicit"
  },
  "prettier.enable": false
}
```

::warning
Da ESLint bereits für das Formatieren des Codes konfiguriert ist, müssen Sie die Funktionalität nicht mit **Prettier** duplizieren.
::

### Typenprüfung

Sie können den Befehl `typecheck` verwenden, um nach Tippfehlern zu suchen:

```bash
pnpm run typecheck
```

### Testen

Bevor Sie eine PR einreichen, stellen Sie sicher, dass Sie die Tests ausführen:

```bash
pnpm run test
```

::tip
Wenn Sie die Snapshots aktualisieren müssen, drücken Sie `u`, nachdem die Tests abgeschlossen sind.
::

### Commit-Konventionen einhalten

Wir verwenden [Conventional Commits](https://www.conventionalcommits.org/) für Commit-Nachrichten, wodurch ein Changelog automatisch generiert werden kann, basierend auf den Commits. Please read the [guide](https://www.conventionalcommits.org/en/v1.0.0/#summary) durch, wenn Sie nicht bereits mit ihm vertraut sind.

- `fix` und `feat` für Codeänderungen, die die Funktionalität oder Logik beeinträchtigen
- Use `docs` für Dokumentationsänderungen und `chore` für Wartungsaufgaben

### Einen Pull-Request erstellen

- [instructions](https://github.com/nuxt/ui/blob/v4/.github/PULL_REQUEST_TEMPLATE.md?plain=1) bei der Erstellung eines PR-Dokuments bereitgestellt werden.

- Stellen Sie sicher, dass der Titel Ihrer PR dem [Konventionelle Ausschüsse ](https://www.conventionalcommits.org/) entspricht, da er nach der Zusammenführung des Codes verwendet wird.

- Multiple Commits sind in Ordnung; keine Notwendigkeit, neu zu basen oder Push zu erzwingen. Wir verwenden `Squash and Merge` beim Zusammenführen.

- Ensure `lint`,`typecheck` und `tests` arbeiten, bevor Sie die PR einreichen.

Wir werden es umgehend überprüfen. Wenn es einem Betreuer zugewiesen wird, wird es sorgfältig überprüft. Ignorieren Sie den roten Text; es ist für Tracking-Zwecke.
